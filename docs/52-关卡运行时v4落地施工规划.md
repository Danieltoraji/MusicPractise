### 1.3 明确不做（v4.0 边界，避免范围蔓延）

- 旧 v1/v3 关卡迁移或兼容运行（v3 数据在 W9 后拒绝加载；不写转换器）。
- 题型资源化（跨关 typeRef/version）：v4.0 题型内嵌在关卡，接口预留 `types[]`。
- 多题并发、题型递归/嵌套调用、跨局持久题态。
- 编辑器移动端适配、AI 复合工具 `edit_level`、多人协作。
- 运行时 UI 大改版：沿用现有舞台 800×470、组件库、皮肤/剧场、音频基础设施。
- 旧 `level.finished` 后置事件体系（由 finish 之后的 flow 继续执行替代）。

### 1.4 「功能超集」的判定标准

1. 10 个样例在 v4 下可完整通关，关键行为（判分、计分、推进、结算、重玩）与 v3 等效或更强；
2. v3 中依赖「答案写死在流程图」的能力，在 v4 必须能通过数据表 + 题单完成；
3. v3 的公开能力（组件库、事件、音频、皮肤、云盘/hub、进度保存、AI 面板、撤销/重做）无回退；
4. 新增：显式题单/牌堆、题型函数复用、四层作用域、结算后流程、预设画廊、按层 AI。

## 2. 总体策略

### 2.1 增量落地 + 终局一次翻转

- **W1–W8 全部为新增模块**（`src/*/v4/`、`schemas/v4/`、`src/sample/v4/`），v3 代码/样例/测试保持全绿，不双改。
- **W9 一次翻转**：替换 10 个样例 JSON、编辑器/播放页切换 v4、`loadLevelDoc` 只收 v4，然后**成组删除** v3 运行时、编辑器、迁移器、旧 schema、旧测试与 fixtures。
- 翻转前任何批次都必须 `npm test` 全绿（v3 + v4 并存）；翻转后重建基线并把新基线写回 AGENTS.md。

### 2.2 单一真源与投影

沿用「单一 IR 三视图」：节点图/伪代码/JSON 是同一 IR 的投影。v4 的 FlowProgram 与 BehaviorProgram 各自有：
- 结构化 IR（真源）；
- 图编辑器视图；
- 伪代码视图（`generate*Script` / `parse*Script` 往返恒等 + 锚点合并）；
- JSON 视图。
三方修改都汇入同一 docState 管线。

### 2.3 接口先于实现

W1 先冻结 `src/engine/v4/model.ts`、`schemas/v4/level.json`、`Selectors/Scopes/Lint` 签名与 Session API（docs/53）。之后各并行流只 + 不改接口；需要改 → 发消息给 Lead，由 Lead 统一改接口并通知所有依赖方。

### 2.4 每批自带 DoD，禁止「先写完再补测」

每个工作项完成时必须带定向测试；每个批次结束时跑：
- `npx tsc --noEmit`
- `npx vitest run <本批相关测试文件>`
- 触及共享门禁（CSS/锚点/文档互锁）时加跑对应静态测试。

### 2.5 样例数据驱动生成

10 个样例不再手写大 JSON，改为 **TS builder 生成 JSON**：
- `src/sample/v4/**` 内用类型安全的 builder 构造 `LevelDocV4`；
- `src/sample/v4/generate.test.ts` 在 `UPDATE_SAMPLES=1` 时写出 `src/sample/v4/*.level.json`；
- 提交 JSON 产物；默认测试做「新鲜度校验」（builder 生成结果 == JSON 文件）与 schema 双校验；
- W9 将产出的 JSON 覆盖到 `src/sample/*.level.json`（文件名/关卡 id/title 保持不变，避免 db 计数、视觉矩阵、导入导出测试的连带改动）。

### 5.2 接口纪律

1. 队友不得修改 `src/engine/v4/model.ts`、`session.ts`、docs/53 定义的签名/语义；需要扩展 → 消息 Lead，由 Lead 改并广播。

3. 运行类功能必须声明 owner 与清理时机（沿用 docs/40 §12.4 纪律）。
4. 新增交互必须带 `data-testid`（G3），不新写类名/文案断言。
5. CSS 只写自己的 v4 css 文件；新增类名可被 G15 扫描到（W9 扩展门禁扫描范围为 `src/**/*.css`）。

### 5.3 合入流程

1. 队友完成工作项 → 自跑 `npx tsc --noEmit` + 定向 `npx vitest run <files>`（必要时 `CONSOLE_GATE_REPORT=1` 查噪音）；
2. 用 `send_message` 向 Lead 报告：完成项、文件清单、测试命令与结果、遗留/风险；
3. Lead 审 diff → 跑全量或相关批次测试 → 提交（每批一组 commit，中文提交信息，沿用仓库风格）；
4. 失败 → 回退/修复清单发回队友；连续两轮不收敛则 Lead 接管该子项。

- W9 删除提交单独一个 commit，便于追溯。
