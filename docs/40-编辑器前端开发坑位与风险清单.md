## 3. A 保存 / 版本 / 校验（数据可信度）

### A1 [P1][新] 保存竞态：await 之后无条件清脏，保存期间的新编辑被当成"已保存"

- **证据**：`src/editor/EditorPage.tsx:224-252`。`save()` 捕获渲染期 `doc` 闭包 → `await db.resources.get` → `loadLevelDoc` → `await putResource`，然后**无条件** `setDirty(false)`（:239-240）；内置示例分支还 `setDoc(result.doc)`（:243），会把保存期间的新编辑回滚成点击瞬间的快照。
- **复现**：Lead 临时用例（§15.2-第 4 条）：把 `db.resources.put` mock 成 250ms 延迟 → 点保存 → 在 await 期间改标题 → 保存完成后**保存按钮的 ` *` 脏标消失**（断言当前缺陷行为）。
- **触发**：点「保存」后继续输入标题/表格（或 AI 轮次仍在 `applyDoc`）；IndexedDB 排队、文档大时窗口放大。
- **影响**：用户看到"已保存"，随后 hash 跳转/关页不再弹确认 → **静默丢最新修改**。后续加自动保存、云同步时，这条链路会被复用并放大为 P0。
- **建议**：保存成功后比对"快照 vs `docRef.current`"（引用/修订号），不一致则保留 dirty 并提示「保存后又有修改」；内置分支不要用 `setDoc` 覆盖，应以保存快照 + 期间编辑重建副本；保存期间按钮进入 pending 态。

### A2 [P1][新] 保存失败没有任何用户反馈

- **证据**：`EditorPage.tsx:224-252` 只有 `try/finally`，没有 `catch`；按钮 `onClick={() => save()}`（:291）丢弃返回的 Promise。`db.resources.get`/`putResource` 抛错（配额满、隐私模式、库被关闭）时无任何 UI 变化。
- **影响**："点保存没反应"与"校验失败（红条）"不可区分；UGC 主流程缺少失败恢复路径。
- **建议**：catch 映射可读中文写入 `saveErrors`；`savingRef` 提升为 state 显示保存中；失败保留 dirty 并提供重试。

### A3 [P1][新] `version` 永不递增，与「同 id 同版本跳过」的导入/云盘规则叠加会静默丢更新

- **证据**：`save()` 原样 `putResource(result.doc)`，编辑器内没有任何升版代码（`EditorPage.tsx:224-247`）；版本只在 `blankLevelDoc`/`copyForEditing` 写死 `0.1.0`（`docState.ts:15,56`）；导入冲突规则"同 id 同 version 跳过、异 version 覆盖"（`src/library/io.ts:132-145`）；契约见 `docs/02-数据结构设计.md:48`「semver，内容变更必须升版」。
- **复现**：§15.2-第 5 条：连续保存两次，`put` 收到的 `doc.version` 都是 `0.1.0`。
- **触发**：编辑 → 导出 → 在已有同 id 记录的机器/云盘再导入（报告"跳过"）；future 云盘同步同理。
- **影响**：导出/导入、云盘更新发布、同 id 兼容策略全部依赖 version，但保存不具备该语义 → 后续做同步/发布时整条链路基线错误。
- **建议**：保存按规则 bump（如 0.1.x 修订号）并在 `savedTip`/导入报告显示新旧版本；或明确裁决"version 仅作者手动改"并把冲突规则改为内容哈希。**（需要一次设计裁决，不能靠实现猜）**

### A4 [P1][新] 迁移/装载失败 → 永久「编辑器加载中…」，错误条不可达

- **证据**：装载 effect 的 catch 里 `setSaveErrors` + `setDoc(null)`（`EditorPage.tsx:138-145`）；但 `!doc` 时提前返回纯"编辑器加载中…"（:259-262），`saveErrors` 只在 doc 非空的返回树里渲染（:299-308）。effect 依赖 `[record, id]`，失败后不会重跑。
- **触发**：打开库内损坏/不可迁移文档、旧 v1 脏数据、或手输 URL 指向非 level 记录（`#/edit/<seriesId>`）。
- **影响**：用户只能看到无限转圈，无法知道原因、无法返回；docs/20 P1-1 声称的"迁移失败转为装载错误条"实际不可达。
- **建议**：把"装载错误"做成独立渲染分支（早于 `!doc` 判断），给可读中文 + 返回资源库/重试。

### A5 [P1][新] 校验错误不可读：英文 JSON Pointer、无「行:列」、oneOf 双分支重复、错误条不截断、UI 无上限门禁

- **证据**：`src/library/validate.ts:69-72` 直接输出 `${instanceLocation} ${error}`（如 `/content/table/rows/3/notes/0/dur`）；`EditorPage.tsx:232-235,299-308` 原样渲染；level schema 是 `oneOf: [V1Level, V3Level]`，cfworker 校验器会收集**所有**失败分支错误（一次失败可上百行）；UI 不校验 schema 上限，到保存才被拒：组件 64 / 视图 32 / 表列 32 / 行 512 / 音符 64（`schemas/v1/level.json:121-136,193-228`、`common.json:31-37`）；列 key/label 长度限制（32/24）同样无输入限制。
- **影响**：UGC 作者面对 `/content/table/...` 无从下手；AGENTS 明确要求「校验错误须带行:列 + 消息」但未落地；后续批量导入/批量出题会把失败面放大。
- **建议**：`loadLevelDoc` 返回结构化错误 `{path,row,col,message}` 并映射中文；表格内联标红；oneOf 失败做二次归纳（只列 v3 分支）；添加按钮按 schema 上限 disabled + `maxLength`。

### A6 [P2][新] 保存成功后不回写规范化后的 doc，内存与库内列类型漂移

- **证据**：普通保存分支只 `putResource(result.doc)`，**不** `setDoc(result.doc)`（`EditorPage.tsx:236-247`）；而 `loadLevelDoc` 内 `migrateDocToV3` 会用行值推断列类型（`engine/migrateDoc.ts:199-208,224-231`）。`addTableColumn` 不写 `type`（`docState.ts:142-149`），内存列无 type → UI 缺省显示 text，库里却可能是 number/json。
- **影响**：同一列"界面显示文本、库里是数字/JSON"；依赖列类型的单元格编辑器、运行时 apply 矩阵、lint 判断错位；下一次保存可能把类型推断成另一种。
- **建议**：`addTableColumn` 显式写 `type:'text'`；保存成功后统一 `setDoc(result.doc)`（同时消除其他规范化漂移）。

### A7 [P2][新] `#/edit/new` 双轨：保存后不切 URL，刷新回到空白模板、再保存可能新建第二条记录

- **证据**：`id === 'new'` 时装载空白模板（`EditorPage.tsx:69-70,134-136`）；save 普通分支不设置 hash（:245-247，只有内置副本分支 :244 跳转）。资源库新建则先 `putResource` 再跳 `#/edit/<id>`（`pages/LibraryPage.tsx:124-133`）——两个入口语义不一致。
- **建议**：`#/edit/new` 首次保存成功后 `history.replaceState` 切到真实 id；或下线该入口，统一走资源库。

### A8 [P2][新] 多标签页/外部写入无冲突检测

- **证据**：`loadedIdRef` 让同 id 的 record 变化不再装载（`EditorPage.tsx:127-146`），Dexie `useLiveQuery` 的更新被拦截；两个标签页编辑同一关卡时后保存覆盖先保存，无提示、无版本检查。
- **建议**：记录 doc 修订号做多标签冲突检测（或明确"单标签"裁决并在 UI 提示）；与 A3 的 version 语义一起设计。

### A9 [观察][新] 首查 150ms 重试是反竞态补丁

- **证据**：`EditorPage.tsx:69-78`：查不到记录时 `await sleep(150)` 再查一次，注释自认"防御 ensureSeeded 与首次查询并发的理论窗口"。
- **建议**：让 `ensureSeeded` 完成信号可被路由层等待（App 已有 `seeded` 状态，可传 context/队列），而不是在编辑器里 sleep。

## 4. B 撤销 / 历史语义

### B1 [P1][已知 + 新细节] 撤销栈按 `update` 次数计（非用户意图）：逐键/逐帧/同值重复各入一条，cap 50 被最常见动作挤爆

- **证据**：`EditorPage.tsx:159-173` 每个 `update` 都 push `structuredClone(cur)`，cap 50（:154-156）；标题逐键（:267-271）；表格 text/number 单元格逐键 commit（`TableGrid.tsx:103-105,322-333,393-397`）；画布拖动/缩放逐 pointermove 提交且**不比对新旧值**（`EditorPage.tsx:448-455,461-472`）。AGENTS 的"高频交互 ref 真源 + 统一 commit"纪律在节点图已执行（`GraphEditor.tsx:602-647`：拖动只写 `dragPos`，落点才 `apply`），画布 Tab 未执行。
- **复现**：§15.2-第 1 条：先改标题 1 次，再模拟一次 60 步拖拽 → 第一次 Ctrl+Z **位置不变**（存在同值历史条）；再 10 次才回退 10px；耗尽撤销栈后标题仍是改后值（原值被挤出 cap 50），画布位置也回不到拖拽前的 40px（最早只能到 50px）。
- **影响**：一次拖动/一段标题输入即可让此前历史全部不可撤销；Ctrl+Z 行为退化为"逐像素回退"甚至"没反应"；配合 B2 还是性能/内存负担。
- **建议**：改为**按用户操作合并历史**：文本输入 debounce/组合，拖动期间用 ref 暂存、pointerup 一次 commit；历史条目改存结构性 patch（或结构共享）；AI 批量写入合并为一条"事务"。

### B2 [P1][新] 画布拖拽/缩放是克隆风暴：每 pointermove 两次整文档深拷贝 + 预览 store 重建 + 全组件重渲染

- **证据**：`EditorPage.tsx:432-476` 的 `onBoxPointerMove`/`onResizeMove` 直接 `onChange(updateComponent(...))`；`updateComponent` 内部 `structuredClone(doc)`（`docState.ts:124-129`），`update` 再 `structuredClone(cur)` 入历史（:164）；`previewStore` 的 `useMemo` 依赖 `doc.content.components`（EditorPage.tsx:480-486）→ 每 move 重建全部组件初始态并重渲染整个预览层（`ComponentView` 全量 map）。
- **影响**：中大型文档拖动明显掉帧；低端机不可用；与节点图正确实现的对比说明这是**可修的现有技术债**，但新增任何"画布级交互"（多选、对齐线、吸附）前必须先收口。

### B4 [P2][新] 无 no-op 短路：未做修改也会标脏入栈（"本局题数"聚焦再失焦即可复现）

### B5 [P2][新] 全局快捷键与焦点语义不完整：Ctrl+Z 穿透弹窗；Delete/Backspace 未排除 SELECT/BUTTON

### B6 [P2][新] AI 写与手动写同栈，但没有事务边界

- **证据**：`update` 是唯一写入口，AI 每个写工具一次 `applyDoc` → 一次 history 条目（`agent.ts:132-148`）；agent 上限 32 轮、每轮可多个 tool_calls；一次长任务可轻松 >50 条写入。checkpoint 是另一套整文档快照（F4）。

### C1 [P2][已知 + 新卸载边界] Tab 条件渲染 = 卸载：画布当前视图、表格列宽/行高、JSON 草稿、AI 输入草稿全丢

- **建议**：抽出统一"编辑器草稿层"（module Map keyed `doc.id` + Tab）覆盖 JSON/表格布局/AI 输入；或 Tab 改隐藏（keep-alive）并只在 `doc.id` 变化时重置。

### C2 [P1][新] 编辑器/路由缺页面级错误边界：只有五 Tab 内容被 `ErrorBoundary` 包住

- **证据**：`EditorPage.tsx:339-368` 的 `ErrorBoundary` 只包五个视图内容；AI 面板在边界之外（:372-385）；页面头部/懒加载 chunk 失败同样无兜底；`App.tsx:96-160` 没有任何路由级 ErrorBoundary，`Suspense` 只给 fallback。

- **建议**：App 增加路由级 ErrorBoundary（含"重新加载/回首页"）；AI 面板单独再包一层；lazy import 失败给可恢复 UI（reload）。

### C3 [P1][新] 调试会话没有宿主生命周期：切 Tab / 离开编辑器后继续跑

- **建议**：由 EditorPage/App 在 graph Tab 卸载或路由离开时停止（对"AI 跨 Tab 启动"可给显式白名单）；会话加 owner/引用计数；全局运行徽标 + 停止入口。

### C4 [P2][新] AI 运行不绑定面板/页面：关面板后隐蔽写入、离开编辑器后静默丢写

- **证据**：`AiPanel.tsx:80-108` 挂载 effect 只做 hydrate/kickoff，**无卸载 cleanup、无 stopAgent**；`agent.ts:50-52` 的 stop 只 abort fetch，工具执行不可中断；写通道是面板的 `applyRef`（`agent.ts:103-111`），面板/编辑器卸载后该引用指向已卸载组件的 `setDoc`（no-op）。运行中关闭 AI 面板（✕）→ 运行继续且仍在改文档，但用户看不到也停不了。

- **建议**：面板卸载即 stopAgent（或显式"后台运行"模式 + 全局运行指示器）；运行归属交给 EditorPage；ToolContext 传 AbortSignal，长等待类工具可取消并回喂"已停止"。

- **建议**：补一条 App 级集成用例（进入编辑器→置脏→点导航→取消→仍在编辑器且内容未丢）；治理重挂（保存内置副本后原地换 id 而非重挂，或明确接受重挂并提示历史清空）。

### F1 [P1][新] AI 运行期用 `runDoc` 影子快照读写，静默覆盖用户同栈手动编辑

- **证据**：`src/ai/agent.ts:99-111` 首笔写后 `getDoc` 永远返回运行内 `runDoc`（注释自认"外部引用会滞后/停摆"）；`AiPanel.tsx:68-71` 的 `docRef` 被 `runDoc` 短路；`tools-write.ts:40,48` 每个写工具读 ctx.getDoc 生成**整文档**再 `applyDoc`。全链路无 base 版本/hash 冲突检测；编辑器在 AI busy 时不锁定（`EditorPage.tsx:374-383`）。
- **触发**：agent 运行（最长 32 轮/可达分钟级）期间用户改画布/脚本/数据表；或面板关闭后用户继续编辑（此时 docRef 冻结，连首笔写都用旧 doc）。
- **影响**：后续写工具基于旧 runDoc 生成整文档，`applyDoc` 回写即静默抹掉用户改动；与"手动与 AI 同栈"的约定冲突；AI 继续基于幻影状态推理。**任何"AI+人工协作编辑"功能都会先撞这条。**
- **建议**：applyAndCheck 前比对编辑器最新 doc 与 mutate 基准（引用/内容 hash），不一致回喂"文档已被手动修改，请先 read 后重写"；或运行期对编辑器加软写锁/冲突标记。

### F2 [P1][新] 流式中断/失败残留 streaming 幽灵消息 + pendingDelta 未清，重试串味

- **证据**：`agent.ts:117` 请求前 `beginStreamingMessage`；`:167-176` catch/finally 只 patch error/busy，不清占位、不清 delta；`session.ts:90,107-119` 的 `pendingDelta` 只在 `streamAppendToLast` 刷帧/`replaceLastMessage` 清除；`:102-104`。
- **触发**：流式请求中途网络错误、用户点停止、供应商 4xx/超时。
- **影响**：①会话永久留一条 `{role:'assistant',streaming:true}` 空/半截消息，面板光标一直闪；②下次重试/新一轮 `history` 从 session 重建（`agent.ts:95`）会把空 assistant 发给供应商，严格网关 4xx →"重试也失败"；③残留 pendingDelta 会在下一轮首帧把旧尾巴拼进新消息；④幽灵消息随 600ms 防抖持久化进 IndexedDB。
- **建议**：catch/finally 中若末条为 streaming 占位则移除或定稿（清 streaming），封装 `discardStreamingMessage(docId)` 清 delta；序列化时过滤 streaming/空 assistant；补"中止-流式"单测。

### F3 [P1][新] 组件契约只下发事件/命令名，payload 说明/props/query/生命周期目录全部丢失

- **证据**：`ai/prompts.ts:121-129` 与 `ai/tools.ts:84-105` 只 `Object.keys(contract.events/commands)`；而 `runtime/componentDef.ts:37-52` 的值就是负载/参数说明（如 `keyClicked: '{ midi: number, name: string }'`、`setMusic: '{ music: MusicDoc }'`），另有 `queries`/`propsDoc`/`propsFields`；人侧已消费这些数据（Inspector `EditorPage.tsx:680-684`、事件面板 `palette.ts:40-47`、生命周期目录 `palette.ts:19-30`），AI 侧全被丢弃。

## 12. 结构性结论：为什么这些坑会反复出现

### 12.1 写路径只有"整文档替换"，没有 patch/事务/修订号

`docState` 23 个函数全部 `structuredClone(doc)` 后改一个字段（`docState.ts:68-280`），`EditorPage.update` 再 clone 一次入历史（`EditorPage.tsx:159-173`）。这带来三个必然结果：

1. 每次按键/每帧拖拽都是 O(文档大小) 的拷贝 → B2/D1 性能问题；
2. 历史只能按"调用次数"记，无法按"用户意图"合并 → B1 历史挤爆；
3. AI 写、手动写、checkpoint、plan 各自持有整文档副本，冲突只能靠"后写覆盖" → F1/F4/E13。

**这是编辑器最大的结构性债**。后续做云同步、协同、自动保存、批量编辑时，必须先引入：文档修订号（revision）、按路径的结构共享/不可变更新（immer 风格）、写事务（一次用户操作=一次修订）、外部写入冲突检测。

### 12.2 "单一真源"存在至少 5 个可写副本，没有统一 stale 框架

除 `doc` 外：ScriptTab `drafts`（唯一带基线签名的实现）、JsonTab `text`、Inspector `propsText`、FlowEditor 非受控题数、AI 的 `runDoc`/`docRef`；另有表格布局态、画布 `view/selected` 等内存态。**只有 ScriptTab 会提示"外部已修改"**，其余要么碰巧同步、要么静默覆盖（C1/D7/E13/G3）。

**建议**：在 EditorPage 引入"文档修订号 + 草稿注册表"：`update` 递增修订号；草稿模块区分 self/foreign 变更；新 Tab 必须实现 stale 策略（提示或自动合并）。

### 12.3 历史语义四套并存，互相打架

| 机制 | 存储 | 粒度 | 持久性 | 问题 |
|---|---|---|---|---|
| 撤销栈 | `EditorPage.histRef` 内存 | 每次 `update` | 刷新/重挂即失 | B1/B3/B6 |
| AI 检查点 | 模块 Map，整文档 | 每次发送/执行计划 | 不持久（session 内存态） | F4/F14 |
| plan 状态 | aiSessions IndexedDB | 计划项 | 持久 | 与文档/检查点脱节 |
| 路由重挂 | `key={hash}` | 页面级 | — | C5 直接清空撤销栈 |

**建议**：收敛为"文档修订号 + 可合并历史"一套模型；AI 任务作为复合事务；checkpoint 作为它的一种标记；路由重挂前显式持久化/提示。

### 12.4 运行归属缺失：debug 与 AI run 都不属于任何页面

`debugRun` 是模块单例，AI run 的写通道挂在面板组件上；两者都没有 owner、没有宿主生命周期、没有全局指示器（C3/C4/E4/F5）。后续任何"后台任务/跨 Tab 运行/多页签"功能都会踩。

**建议**：抽一个 `EditorRuntime` 层：由 EditorPage 持有生命周期；每个运行有 `owner` 与 `docId`；路由离开/组件卸载统一 cancel；全局运行徽标。

### 12.5 主题与契约靠"逐条人工维护"，没有机制

- 主题：浅色=全局 token、深色=124 组 `.ge-dark` 逐条覆盖 + `--ge-*` 双写 fallback；派生 token（focus-ring/shadow）只在 `:root` 计算（G2/G4/G8/G13）。每新增一个控件都要手写对偶规则。
- 契约：组件 events/commands 的**值**（payload 说明）只有人侧 UI 消费，AI 侧丢弃（F3）；列类型 7 处同步（D6）；工具 JSON Schema 手写双清单（F19）。
- 测试：DOM class/文案被 200+ 处硬锁（G3）。

**建议**：①`.ge-dark` 改为"在根上重映射语义 token"，消费方仍写 `--panel/--ink/--accent`（一次性消灭双写）；②契约从 `componentDef` 派生给 AI 与工具 schema；③测试改用 `data-testid`/role。三者都是"机制替换人工"的投入，越晚做成本越高。

### 12.6 验证缺口：CSS 无回归、jsdom 无 canvas、无 lint、无浏览器 E2E

详见 H2/H4/G3。当前质量门禁只有 `npm test`（808）+ build；编辑器最贵的部分（视觉、拖拽、画布渲染）恰好是自动化覆盖最薄的部分。
