# 56 · 关卡运行时 v4.1：题型内视图与全局时钟

> 状态：**已落地并验收**（2026-10-27）
> 前置：docs/51 设计种子、docs/52 施工规划、docs/53 规格冻结、docs/54 实施记录、docs/55 最终验收
> 范围：只做「题型内视图（surface.views）+ 全局时钟（run.elapsedMs）」两项增量，**不动 v4 的 Flow/Behavior 分层与计分/结算语义**；不引入运行时策略枚举，新增能力仍以普通 IR/普通绑定表达。

---

## 1. 背景与裁决

v4 落地后暴露出两个真实缺口（用户 2026-10-27 讨论确认）：

1. **视图只在关卡层**：`shell.views` + shell 组件 `view` 必填；surface 组件禁止 `view`，behavior 也没有切视图节点。题内分步（读题 → 作答 → 反馈）只能逐组件 `call setVisible`，或把一个逻辑题拆成多个题型。
2. **没有跨题时钟**：`run` 只暴露 `questions/total/seed/index`；shell 计时器在题中 tick 事件被丢弃、behavior 无法读取；无法做“本关用时”实时显示或整关限时。

裁决：

- **视图作为「层内渲染过滤」概念同时存在于两层**：`shell.views`（关卡/跨题，flow `setView` 切）与 `surface.views`（题型/题内，behavior `setView` 切）。同一个 `setView` 节点 kind 按层解释，语义对称。
- **全局时钟做成只读 `run.elapsedMs`**，不新增组件类型、不引入 `timerPolicy` 之类枚举：表达式/绑定直接读；有 UI 绑定时由 session 以 100ms 刷新绑定；`debug` 暂停冻结、`finish` 定格、`restart` 归零。
- 两项能力都**不改变**“题内交互归题型、关卡进程归 flow、计分账本归 `v.score`”的既有裁决。

## 2. 题型内视图（surface.views）

### 2.1 数据模型

```ts
interface QuestionSurface {
  views?: ViewDef[]          // 题内视图（≤16）；省略 = 无题内视图
  initialView?: string       // 省略 = views[0]；每次 ask 从它开始
  components: ComponentInstanceV4[]
}
```

- `surface` 组件 `view?: string`：**省略 = 所有视图都渲染**（题面/反馈等常驻件）；填写 = 仅该视图渲染。
- 视图 id 与 shell 视图同一形态（本地 id）、题型内唯一；壳层与题型层命名空间独立。
- `initialView` 必须属于 `views`；有 `initialView` 必须有 `views`；`views` 不允许空数组（不需要视图请省略）。

### 2.2 运行时语义

- surface 帧新增 `view`，`ask` 挂载时取 `initialView ?? views[0]`；**每次 ask 重新从初始视图开始**。
- `behavior` 新增 `setView` 节点（与 flow 的 `setView` 同一 kind）：
  - flow 层：切 `shell.views`（原有行为不变）；
  - behavior 层：切当前帧的题内视图；无题内视图/视图不存在 → 运行日志 error，不改变视图。
- 切视图**只过滤渲染**：组件 store 不重建（同一题内组件内部状态、计时器保留），`q.state`/`t` 持久。
- 未声明 `view` 的组件在所有视图渲染；声明了的组件只在对应视图渲染。
- 渲染层：`LevelStageV4` 用 `filterSurfaceComponents(components, view)` 过滤；`.v4-surface` 带 `data-view` 供测试/视觉断言。
- 调试/快照：`V4Snapshot.surface` 增加 `view`；`V4DebugState.scopes.run` 亦可见 `elapsedMs`（见 §3）。
- 与 shell 视图的差异（有意）：shell 视图跨题持久由 flow 控制；题内视图随每次 ask 重置，由 behavior 控制。

### 2.3 校验与 lint

- `V4_REF`：surface 组件 view 悬空、`initialView` 悬空、有 `initialView` 无 `views`、`views` 为空数组。
- `V4_DUPLICATE_ID`：题内视图 id 重复。
- `V4_LIMIT`：题内视图 > 16（`SCHEMA_LIMITS_V4.surfaceViewsPerType`）。
- `V4_NODE`：behavior `setView` 的 view 不在本题 `surface.views`（validate 按层传入视图集合）。
- schema：`Surface.views/initialView`；`BehaviorNode.kind` 枚举增加 `setView`；shell 的 `setView` 校验逻辑不变。

### 2.4 编辑器 / 伪代码 / AI

- **题型 → 表现**新增「题内视图」子卡：新增/改名/设为初始/删除；每个 surface 组件出现「视图归属」下拉（全部视图 / 各视图）。
- 删除视图不删组件：归属该视图的组件改为「所有视图可见」；删除最后一个视图时一并移除 `initialView`。
- docStateV4 新增纯函数：`addSurfaceView/updateSurfaceView/removeSurfaceView/setSurfaceInitialView`（结构共享、恒返回新对象、id 程序化）。
- behavior 图工作台：调色板在题型存在视图时提供「切换视图 view」；检查器视图下拉按层取 `shell.views` / `surface.views`。
- 伪代码：behavior 支持 `view '<id>'` 语句生成与解析（与 flow 同一语句形态）；锚点合并保留 `setView` 节点。
- AI：prompt/read_layer 带出题内视图与 `run.elapsedMs` 说明；写工具仍走同一 `loadLevelDoc` 预检（悬空视图会被拒绝）。

## 3. 全局时钟（run.elapsedMs）

### 3.1 语义

- `run.elapsedMs`：本局开始（`start()`/`restart()` 重置）后的累计毫秒，整数；`run` 仍为只读作用域。
- 时间源：`host.getNowSeconds?.()`（音频时钟）否则 `performance.now()/1000`；与 `now()` 表达式函数同源。
- 生命周期：
  - `start()`/`restart()`：归零（restart 后重新计时）；
  - `finish`：**定格**（结算后 flow 还可继续 `waitShell`，但时钟不再增长）；
  - flow 自然结束/错误结束：定格；
  - debug `setTimersPaused(true)`：冻结（暂停区间不计入 elapsedMs）；`false` 恢复；
  - `dispose`：停止刷新定时器。
- **实时显示**：shell/surface 组件的 bindings 可写 `run.elapsedMs`（例如 `'⏱ ' + floor(run.elapsedMs / 1000) + 's'`）。session 检测到任意 shell/surface 绑定引用 `run.elapsedMs` 时，启动 100ms 刷新定时器（`CLOCK_TICK_MS`）：重算 `elapsedMs` → `syncBindings()` → 按值变化下发组件命令。
  - 没有时钟绑定时**不启动**定时器（纯逻辑读取在每次表达式求值时现算，无 tick 开销）；
  - 刷新只走绑定命令，不触发作者逻辑、不写作用域。
- 行为/流程读取：`behavior` 事件求值与 flow 表达式求值前刷新 `elapsedMs`，因此事件处理器读到的 `run.elapsedMs` 是**事件时刻**的实时值。
- 题中可见：shell 绑定在题目执行期间也会随 tick 重算（与“shell 事件被忽略”不冲突——绑定是只读投影，不是作者逻辑）。

### 3.2 边界（v4.1 明确不做）

- 只提供 `elapsedMs`（毫秒），不提供格式化成秒/分或倒计时；作者用 `floor/round` 自行格式化。
- 不提供 `run.deadline/remainingMs` 或整关限时策略；需要整关限时时由 flow 维护 `v.deadline`/ask args，题型内用 `now()`/`run.elapsedMs` 判定（不引入平台策略枚举）。
- tick 粒度 100ms；不保证逐帧/精确定时。
- 没有 UI 绑定时不会为“显示”自动刷新；若要显示时钟，必须写绑定（AI/编辑器都会提示）。
- `run.elapsedMs` 仅点号路径可检测（`run.elapsedMs`）；不要用 `run["elapsedMs"]`（检测不到 tick）。

### 3.3 示例

shell 组件（HUD）：

```json
{
  "id": "clockLabel",
  "type": "label",
  "view": "main",
  "layout": { "x": 460, "y": 12, "w": 180, "h": 28 },
  "bindings": { "text": "'⏱ ' + floor(run.elapsedMs / 1000) + 's'" }
}
```

behavior 事件里读实时值：

```text
on choice1.chosen {
  q.state.t0 = run.elapsedMs   // 记录事件时刻
  ...
}
```

## 7. W12 补丁：behavior foreach（v4.2）

### 7.1 背景与裁决

行为节点集此前有 branch/loop（while/repeat）但缺 `foreach`；引擎层 `execSharedNode` 早已实现 foreach，flow 调色板也可用，只是 behavior 的模型/校验/脚本/编辑器未登记。裁决：**把 foreach 按共享节点开放给 behavior**（不新增运行时语义），同时修复行为任务共享 `WalkFrame.loopState` 的问题。

### 7.2 改动

- 模型/schema：`BehaviorNode` 联合增加 `ForeachNode`；`schemas/v4/level.json` 的 `BehaviorNode.kind` 枚举增加 `foreach`。
- 校验/lint：`BEHAVIOR_KINDS` 增加 `foreach`；foreach 的 `items/itemVar/indexVar` 走共享字段校验；lint 把 `itemVar/indexVar` 视为**隐式 local**（无需 `behavior.locals` 声明），并对 `items` 做表达式路径校验。
- 运行时：`execSharedNode` 原样复用；**BehaviorRunner 每个任务创建独立 `WalkFrame`**（此前所有并发任务共享一个 loopState，同一 handler 被重复事件触发时 repeat/foreach 游标可能互相消耗）。flow 仍为单任务/单 frame，不受影响。
- 伪代码：behavior 生成器支持 `foreach item, i in <expr> { ... }`（与 flow 同构），解析器原本已接受；`graphNodeKey` 不再把 behavior foreach 标为非法；锚点合并保持。
- 编辑器：behavior 调色板「控制流」增加「遍历 foreach」（默认遍历题型表中首个 list/json/notes 列，否则 `[]`）；检查器 hint 按层区分；节点卡摘要增加「遍历」。
- AI prompt 的 behavior 节点清单补 `foreach`。

### 7.3 语义

- `foreach` 首次进入对 `items` 求值一次并快照；`true` 出口进体，体尾回边回 foreach 推进；`false` 出口继续。`itemVar/indexVar` 写 `local`，每次迭代覆盖；循环结束后保留最后一次值。
- 与 flow 的差异只在作用域/可访问组件（behavior 只允许本题 surface、不能写 `v.*`），节点语义一致。
- 并发：同一事件被多次触发时每个 handler 任务独立遍历；`local` 仍是**每次 ask 调用共享**的（任务间覆盖遵循既有任务交错规则），但循环游标不串。
